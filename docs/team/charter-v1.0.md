## 2. 团队价值观

1. **可评审优先**：任何产出的判断标准是"队友能否在 10 分钟内看懂并给出意见"。
2. **小步提交**：一次提交只做一件事，宁可多提几次，也不提交一大坨。
3. **对事不对人**：评审针对代码与文档，不针对个人；被指出问题时先确认事实再讨论。
4. **不甩锅、不留坑**：接手他人代码前先读，改完必须补测试或说明。
5. **进度透明**：任务状态当天更新到看板，卡住超过半天必须发声。

## 3. 沟通约定

- **日常沟通**：微信群为主，技术决策与结论必须落到 Issue / PR 评论里，避免只在聊天里说。
- **响应时间**：工作时段内消息 2 小时内回复；轮到评审时 24 小时内给出意见。
- **会议节奏**：
  - Sprint 计划会：每个 Sprint 开始时，30 分钟；
  - 每日同步：线上文字同步，阻塞问题直接 @ 队长；
  - Sprint 评审 + 回顾：每个 Sprint 结束时，45 分钟。
- **会议产出**：每次会议结束 24 小时内，由队长在 `docs/` 下补纪要。

## 4. 开发规约

### 4.1 分支模型

- `main`：只接受来自 `dev` 的合并，始终保持可演示状态。
- `dev`：默认分支，日常集成分支，所有功能与文档 PR 的目标分支。
- `feature/<功能>`、`docs/<主题>`、`fix/<问题>`：从 `dev` 切出，完成后向 `dev` 提 PR。
- 禁止直接向 `main` 或 `dev` 推送代码。

### 4.2 提交信息

遵循 Conventional Commits：`<type>(<scope>): <描述>`
常用 type：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
示例：`docs: add caowen hello introduction`、`feat(qa): implement question voting`。

### 4.3 Pull Request

- 每张 PR 必须：说明改了什么、为什么改、如何验证。
- 每张 PR 至少 1 名队友 **Approve**，并在评论文本中写明 `LGTM`。
- **禁止自评自合**：作者不能批准自己的 PR；合并统一由队长执行。
- 评审意见分三级：`must`（必须改）、`should`（建议改）、`nit`（吹毛求疵，可不改）。
- 合并方式统一使用 Merge（保留提交历史），合并后删除源分支。

### 4.4 代码与文档质量

- 后端遵循 DDD 模块边界，跨模块只通过 `api` 包交互（由 ArchUnit 适应度函数守护）。
- 新增或修改业务逻辑必须伴随单元测试；测试先红后绿。
- 中文文档统一 UTF-8 编码，文件名使用英文小写加连字符。

## 5. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

1. 代码已提交并推送到远端分支；
2. 单元测试通过（`mvn test` 无新增失败）；
3. 构建通过（后端 `mvn compile`、前端 `npm run build`）；
4. 至少 1 名队友 Approve 且留下评审意见；
5. PR 已合并进 `dev`；
6. 看板卡片已移动到 Done。

## 6. 决策与冲突

- 技术方案分歧：先各自在 PR 或 Issue 里写清利弊，48 小时内未收敛则由队长拍板并记录理由。
- 排期冲突：优先保证 Sprint 目标，必要时砍需求而不是砍质量。
- 成员失联超过 48 小时：队长介入重新分配任务，避免阻塞整个 Sprint。
